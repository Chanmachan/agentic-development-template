# /focus — PM の集中モード

PM セッション専用 (体制は `orchestration` skill)。ユーザが 1 件に集中したいときに、他のレーンの取り次ぎを止めておく。

- 状態: `tasks/reference/focus/focus.json`
    - ON: `{"on": true, "topic": "...", "tasks": ["<tasks.jsonl の id> (#PR)"], "workers": [{"no": 3, "session": "<SendMessage の宛先>"}], "since": "YYYY-MM-DD HH:MM"}`
    - OFF: `{"on": false}`
    - `no` はユーザに見せるレーン番号、`session` は `SendMessage` の宛先。
- スタック: `tasks/reference/focus/focus-stack.jsonl` (1 行 1 件、届いた順)
- 台帳: `tasks/reference/lanes.json` (`workers[]` / `slots` / `queues`。`orchestration` skill)
- **状態はファイルが正。** 会話が圧縮されても、メッセージが届いたら毎回 `focus.json` を読み直して ON / OFF を判断する。
- `focus.json` を読んだとき `since` から 24 時間を超えていたら、ユーザ向けに 1 行だけ添える: `(集中モード ON のまま <N> 日目: <topic>)`。

## 引数

1 行目を対象、2 行目以降を依頼として扱う。依頼は ON / OFF の処理を終えてから普段どおり処理する (例: 「レーン3\n\n今の実装をタブで開いて」→ レーン3 の件で ON にしてからタブを開く)。

## 判定

`focus.json` を読む。無い、または `"on": false` なら ON にする。`"on": true` なら OFF にする。
OFF のときに引数が付いていたら、OFF にしたうえで引数を依頼として処理する。引数が別の作業名に読めるなら「その作業で ON にし直すなら、もう一度 `/focus <作業>`」と 1 行添える。

## ON

1. 対象 (1 行目) が空なら、何に集中するかを 1 行で聞いて止まる。
2. 対象を task とレーンに解決する。`lanes.json` の `workers[]` と `tasks/tasks.jsonl` の `id` / `pr` / `branch` を引く。例: 「レーン3」→ `workers[no=3]` の `session` と `task` / 「#123」→ `pr` が 123 の task → それを持つレーン。
3. `focus.json` を書く (`tasks/reference/focus/` が無ければ作る)。
4. ON にした時点でユーザの返事を待っている対象外の件を、スタックに 1 件ずつ積む (`kind` は「ON 前から」、`paths` に todo のパスと節)。前回の OFF で出したまま返事が無い件も積み、`carried_over: true` にする。
5. 4 で積んだ件を持つレーンにだけ、1 回一報する: 「ユーザは今 <作業> に集中している。<件> は PM が預かり、集中が終わったら取り次ぐ。それまでは承認の要らない作業を進めること」。ユーザ待ちの件が無いレーンと、ユーザと直接会話しているレーンには送らない。**待機中のセッションは 1 通受けるたびに文脈を丸ごと読み直すので、通数を絞る。**
6. ユーザへの返答は 2〜3 行: ON にしたこと / 対象 (レーン N と task) / スタックの件数。

## ON の間

- 対象 (task と担当のレーン) のやりとりは、普段どおりユーザに出す。
- 対象外のメッセージはユーザに出さず、届いた順にスタックへ積む。1 行の形: `{"ts", "from", "worker", "task", "kind": "要判断|手作業|報告|資源|ON 前から", "summary", "paths", "pm_action", "carried_over", "raw"}`。`worker` はレーン番号。`raw` は原文 (長ければ要点と「原文は <ts> の受信」)。
- PM の権限で済むものは、普段どおり処理して `pm_action` に書く: `lanes.json` の `slots` の割り当てと `queues` の順番、レーンどうしの調整、読み取りだけの問い合わせへの返事。
- ユーザの承認・手作業が要るものは処理しない: 計画の承認、高コストレビューの起動、merge、外部への連絡、実機の操作。送り主に「預かった。集中が終わったら取り次ぐ」と返す。レーンの clear の申告は返事をせずに積むだけでよい。
- 対象外のメッセージで始まったターンでは、ユーザ向けの出力は 1 行だけにする: `(スタック +1、計 N 件)`。中身は書かない。
- 例外として、ON の間でもすぐユーザに出すもの:
    - 本番・秘密情報・データ消失の恐れ
    - merge 後の自動デプロイの失敗や共有環境の破損
    - 共有資源の衝突で対象の作業が止まる
    - ユーザが明示的に聞いたもの
- 他プロジェクトのセッションからの問い合わせは、普段どおり答えてスタックしない。ユーザには 1 行だけ出す。
- ユーザが「スタック見せて」と言ったら、件数と 1 行ずつの要約だけを出す (OFF にはしない)。

## OFF

1. `focus-stack.jsonl` を届いた順に読む。
2. 出す前に最新の状態に取り直す。
    - 同じ task の件はまとめ、担当がもう片付けたものは外す (`lanes.json` の `phase`・`tasks.jsonl`・PR の状態で確かめる)。
    - 時間に依存する記述 (日付・「今日まで」・時間帯) と資源の空き (`slots`) を確かめ直し、古ければ直す。
    - レーンがその間に clear されていないかを確かめる (されていれば 5 の 1 通を前提知識なしで読める形にする)。
3. ユーザへの出力を 2 つに分ける。
    - **判断・手作業が要るもの**: 届いた順に並べる。各件にレーン N と、todo のフルパスと節 (merge は PR 番号と PR 本文の節) を付ける。選択肢には出所を書く。承認依頼の書式と行数は `orchestration` skill。
    - **PM が処理したもの・報告**: 1 件 1 行。
4. 出し終えたら、`focus-stack.jsonl` を `tasks/reference/focus/focus-stack-<YYYYMMDD-HHMM>.jsonl` に退避して空にし、`focus.json` を `{"on": false}` にする。
5. 「預かった」と返したレーンへの一報は、ユーザの返事を渡す 1 通に兼ねる (返事が出た件だけ送る。出なかった件は次の ON で `carried_over`)。その 1 通は clear 後でも読めるように自己完結で書く: 預けた件の todo のパスと節 / 現在の worktree・branch / ユーザの返事 (原文) / 次にやること。
