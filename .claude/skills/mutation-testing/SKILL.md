# Mutation testing

テストが緑でも、そのテストが壊れた実装を検出できるとは限らない。実装をわざと壊して赤くなることを確かめる。worker の「直した」もレビュアーの「修正済み」「この変異でも緑」も、自分で撃つまで信じない。

## 手順

1. **退避** — 変異対象ファイルの一覧を作り、退避コピーを取る。修正ラウンドごとに作り直す (使い回すと、テスト自身への変更が退避に無く汚染する)。撃つ前に一覧と退避のファイル数を突き合わせる。
2. **到達確認** — 変異点がテストの経路上にあることを、一時的な throw 等で先に確かめる。経路外の変異は全部緑でも意味が無い。
3. **1 つずつ撃ち、1 つずつ戻す** — 複数を同時に入れると、別理由の赤を「効いている」と誤認する。
4. **実行件数を毎回見る** — 通常と同じ件数が走り、その中の 1〜2 件が落ちるのが「検出」。件数 0 や激減の回は無効 (構文が壊れても赤になる)。
5. **後始末** — 終わったら退避と突き合わせて全部戻し、変異の残存が 0 であることを `grep` で確かめる。残った変異がそのまま commit されると、実装バグに見える (絞ったテストは緑・フルだけ赤)。

## 緑になったら疑う

変異を入れても緑のとき、原因は次のどれか。どれか分かるまで「テストが弱い」と決めつけない。

- **テストが弱い** — 本当の検出漏れ。表明を足す。
- **テストが実行されていない** — skip・フィルタ・環境変数不足で無言 skip、0 件登録。撃つ前に登録件数・実行件数を出して変異表の本数と突き合わせる。
- **変異が狙った経路に当たっていない** — 到達確認 (手順 2) を飛ばしている。
- **当たったが自己修復した** — 直後の再取得などの非同期処理が上書きして症状が一瞬で消える。その非同期を pending のまま握ってから表明する。
- **同じガードが 2 箇所ある** — 1 つ外してももう一方が守る。1 つずつ外すと全部緑・両方外すと赤なら冗長。1 本に寄せる。
- **今の設計では正しく無効** — 計画レビュー等で処方が変わり、ガード自体が不要になった。期待する赤の表を処方変更のたびに作り直す。

## 変異の選び方

- helper にだけ変異を入れると、呼び出し側の配線漏れ・置き換え漏れが素通りする。呼び出し側を 1 箇所ずつ旧実装に戻す変異を必ず加える (旧新で結果が変わる入力だけ)。
- 否定のアサーション (`not.toContain` 等) は、隣の要素が消えても通る。守りたい要素は肯定で表明する。
- 「並べ替えても失わない」系の検査は対照を 3 つ取る (並べ替え → 差分 0 / 改竄 → 検出 / 削除 → 検出)。その前に入力が空でないことを表明する (不在ファイルどうしの比較は常に一致する)。
