# Orchestration

役割と規律の正本は `.claude/rules/model-roles.md`。ここはその運用の詳細。

## 体制

- **PM** — ユーザがセッション単位で指名する 1 本。レーンへの割り振り、共有資源の台帳、ユーザへの取り次ぎ (承認・手作業) を持つ。
- **レーン** — PM から 1 タスクを受け持つセッション。orchestrator の分身で、実装はしない (`model-roles.md`「レーンの実装規律」)。
- **worker** — brief 単位で実装する。
- 区切り (スライス) ごとに clear する: レーンが報告 → PM が処理 → ユーザが clear。brief と引き継ぎは clear 後でも読めるよう、それだけで分かる形に書く。
- PM の集中モード (1 件だけユーザとやりとりし、他は預かる) は `/focus`。

## 共有資源の台帳

`tasks/reference/lanes.json` (git 管理外)。**PM だけが書く。**

```json
{
  "workers": [{"no": 1, "session": "<SendMessage の宛先>", "task": "<tasks.jsonl の id>", "worktree": "<絶対パス>", "phase": "<自由記述>"}],
  "slots": {"<資源名>": "<持ち主の session> | null"},
  "queues": {"<資源名>": ["<待っている session>"]}
}
```

- 資源名はプロジェクトで決める (例: 共有ローカル DB、dev server のポート、migration 番号、依存の install)。
- 排他の資源は 1 つにつき持ち主 1 人。
- 使う前に PM に申告し、**返事を待ってから**使う。「一報した」だけで使い始めると衝突は止まらない。
- ユーザが直接承認していても、持ち主は台帳で確かめる。

## 報告と承認依頼

- 通常の報告は **15 行以内**。詳細は `tasks/<id>-todo.md` 末尾 (完了後は `tasks/done/<id>.md`) に書いてパスを渡す。
- 報告には実装した主体 (どの worker / 手直し) を書く。
- **承認依頼** (merge / 高コストレビューの起動 / スコープ逸脱等) は判断材料込みで **30 行まで**: 選択肢・根拠・推奨、計画ファイルのパスと節 (merge なら PR 番号と PR 本文の節)。
- 選択肢には出所を書く (ユーザやクライアントが書いたものか、AI が考えたものか)。
- 承認は 1 件ずつ取る。一括承認を次の件に持ち越さない。

## worker brief

起動前に、自分 (orchestrator / レーン) の未コミットの作業を commit しておく。

brief に必ず入れる行:

- 「`git checkout` / `restore` / `stash` を撃たない。スコープ外の差分は戻さず報告する」
- 「コメントを追加しない。copy-adapt 時も元コメントを複製しない。制約はテストで表明する」 (`.claude/rules/comments.md`)
- エスカレーション基準 (`model-roles.md`) — 計画に無い設計判断 / 同じエラーで 2 回失敗 / 保護ファイル・スコープ外 / テストを弱める以外に手がない
- 検証コマンドと、報告の形 (行数・含める項目)
- プロジェクト固有の既知ノイズ (失敗に見えて失敗でない出力) があればその一覧

## worker の diff を確かめる

- diff は全部開く。自己申告を信用しない。
- 書き換えたテストは、base の blob (`git cat-file blob <base>:<path>`) と assertion の件数・種類を突き合わせる。assertion が黙って減ってもテストは緑のまま。
- 「直した」は mutation で実測する (`mutation-testing` skill)。

## レビュー経路

- 主レビュアー → fallback 1 → fallback 2 の段を先に決めて書いておく (例: 別ベンダーの CLI レビュー → 同じモデルを別経路で → Claude の `review-*` subagent 並列)。どれかが使えないことを理由に品質ゲートを飛ばさない。
- 全観点を 1 pass で横断させると stall しやすい。観点を 2 本ずつに絞った pass を並列に回す。
- Blocking の採否は、該当ファイルを開いて裏取りしてから決める。棄却理由も todo に残す。

## 調査の委譲と裏取り

- subagent への一斉展開は数本まで。広い調査を一度に振ると再帰的に spawn されて利用上限で全滅する。
- subagent の報告にある `file:line` は、自分で開いてから計画に書き写す。
- 「無い」「必ず」は 2 つの方法で確かめる (一覧に無い + 実際に引いても見つからない)。
- 他レーンの診断を「同じ型だ」と決めつけて適用しない。自分の側でも対照を取る (測らずに直した変更だけが残る誤診伝播を防ぐ)。
